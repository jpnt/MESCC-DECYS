## The protocol this report attacks

IEEE 802.11 carries frames unencrypted unless a key is installed. WPA2
(standardised as IEEE 802.11i) establishes those keys with a four-party
exchange called the 4-way handshake, part of the RSNA state machine:

1. The authenticator (AP) sends an ANonce.
2. The supplicant (client) replies with an SNonce; both sides can now
   derive the **PTK** (pairwise transient key) from the PMK, both
   nonces and both MACs.
3. The AP sends EAPOL-Key frame 3 of 4, carrying its **Key-Data**
   (the GTK) and, in the **Key-Info** field, the **Install** bit:
   *"install the PTK into your now unicast-keyed hardware now."*
4. The supplicant sends frame 4 of 4; the AP installs its receive key.

Two properties of this design matter for everything below. First, CCMP —
the mandatory cipher — is AES in **counter mode**: security holds only
while the (key, nonce) pair is never repeated, and the nonce is built
from the transmitter's **packet number (PN)**, initialised when the key
is installed. Second, 802.11 link-layer acknowledgements are unreliable,
so *every* handshake frame is expected to be **retransmitted**, and
implementations must tolerate receiving the same message twice. KRACK
(CVE-2017-13077 and family [@krack] [@krack-site]) is the observation
that these two requirements collide: a supplicant that tolerates a
repeated Message 3 *by re-running its installation* resets the TX PN to
zero with the same key — and counter-mode keystream is reused against
two different plaintexts. The cipher is never broken; its *nonce* is.
The same key-installation logic is why the AP's retransmitted GTK
installations (KRACK #3/#4) matter: for most chipsets the relevant
detail is *how* a key gets installed, not whether the math is sound.

WPA3 replaces the PSK-based 4-way handshake with **SAE** ("Dragonfly",
RFC 8032): mutual authentication by a zero-knowledge password proof.
Both sides commit to a value (blind = v+m) and to a curve point
(commit = v*G − PWE, where the PWE is a point *hunted* from the
password), then confirm against a derived key. Its two 2019 failures
(Dragonblood, CVE-2019-9494–9499 [@dragonblood]) are, again, about state
and channels, not the maths: the standard's reference flow lets
commitments be *reflected*, and the password-to-point hunt runs a
*variable-length* loop whose work a cache-timing attacker can observe.
