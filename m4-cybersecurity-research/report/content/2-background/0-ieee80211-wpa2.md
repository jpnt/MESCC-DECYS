## The protocol this report attacks

IEEE 802.11 carries frames unencrypted unless a key is installed. WPA2
(standardised as IEEE 802.11i) establishes those keys with the 4-way handshake, part of the RSNA state machine:

#figure(
  table(
    columns: 4,
    inset: 6pt,
    table.header([*Msg*], [*Direction*], [*Carries*], [*Effect on the client*]),
    [1/4], [AP to client], [ANonce], [start PTK derivation],
    [2/4], [client to AP], [SNonce], [complete PTK inputs],
    [3/4], [AP to client], [KCK-MIC, *Install bit*, GTK + RSC in Key-Data], [install PTK (resets TX PN when Install is set), reply 4/4],
    [4/4], [client to AP], [MIC over the 3/4 context], [AP installs its receive key; port authorized],
  ),
  caption: [The four-way handshake: EAPOL-Key message roles (from the protocol description in the original paper [@krack]).],
) <tbl-fourway>

The four message roles above are the exact surface our Chapter 3 model
replays. Two properties of this design matter for everything that
follows: how the derived key material is *split* between the handshake
and the radio, and what the standard *requires* a client to do when
the same handshake message arrives twice. The rest of this section
works both out from the checked-in sources and from the papers' own
quotations of the standard.

### From passphrase to keys: PMK, PTK, and the KCK/KEK/TK split

In WPA2-Personal the PMK is not the passphrase. It is a fixed 32-byte
expansion of it, salted by the network name: `PMK =
PBKDF2-HMAC-SHA1(passphrase, SSID, 4096, 32)`. `wpa_supplicant` 2.3
computes exactly that, `pbkdf2_sha1(ssid->passphrase, bss->ssid,
bss->ssid_len, 4096, psk, PMK_LEN)` in `wpa_supplicant/wpa_supplicant.c`
with `#define PMK_LEN 32` in `src/common/wpa_common.h`, both paths
inside the pinned `lab/wpa_supplicant-2.3.tar.gz`. The implementation's
own header names the normative source: "IEEE Std 802.11-2004, Clause
H.4. The main construction is from PKCS#5 v2.0"
(`src/crypto/sha1-pbkdf2.c`). Two consequences are worth noting before
the attack is even in view. The salt is the plaintext SSID, so every
access point advertising the same name yields the same PMK for the same
passphrase. And the 4096 iterations make the derivation deliberately
expensive, which is what classifies PMK recovery as an
offline-dictionary problem rather than a handshake problem; none of the
attacks in this report touches it. In an enterprise network the same
32-byte PMK is instead handed over by the 802.1X method
(`eapol_sm_get_key(sm->eapol, sm->pmk, PMK_LEN)`, same file), which is
why the 4-way handshake and everything below it is identical in both
flavours.

The PTK is a PRF expansion of the PMK over the fresh handshake inputs,
and the whole key hierarchy is one line. Verbatim from
`src/common/wpa_common.c` of the pinned 2.3 release:

```c
/*
 * IEEE Std 802.11i-2004 - 8.5.1.2 Pairwise key hierarchy
 * PTK = PRF-X(PMK, "Pairwise key expansion",
 *             Min(AA, SA) || Max(AA, SA) ||
 *             Min(ANonce, SNonce) || Max(ANonce, SNonce))
 */
```

`wpa_pmk_to_ptk()` in that file realises the ordering rules byte for
byte: it `os_memcmp`s the two MAC addresses and copies the numerically
smaller to `data[0:5]`, the larger to `data[6:11]`, then does the same
for the 32-byte nonces at `data[12:43]` and `data[44:75]`, and calls
`sha1_prf` over `label || data` (`use_sha256` selects `sha256_prf`
instead, the SHA256-based AKMs that arrived with 802.11w). The label is
the literal string `"Pairwise key expansion"`, passed in by
`wpa_derive_ptk()` (`report/snippets/upstream/wpa_23.c`). The min/max
ordering exists so both peers reach the same concatenation without
first agreeing which of them is AA and which is SA. Two things follow
directly. The nonces travel in the clear, so the only secret input to
the KDF is the PMK; and the PTK is refreshed on every handshake
precisely because the nonces are. The output length is not arbitrary
either: `wpa_derive_ptk` asks for exactly
`wpa_cipher_key_len(sm->pairwise_cipher) + 32` bytes, i.e. for CCMP, 16
bytes of cipher key plus a fixed 32-byte overhead.

That output is consumed as disjoint slices, laid out in `struct
wpa_ptk` in `src/common/wpa_common.h` of the same release:

```c
struct wpa_ptk {
	u8 kck[16]; /* EAPOL-Key Key Confirmation Key (KCK) */
	u8 kek[16]; /* EAPOL-Key Key Encryption Key (KEK) */
	u8 tk1[16]; /* Temporal Key 1 (TK1) */
	union {
		u8 tk2[16]; /* Temporal Key 2 (TK2) */
		...
	} u;
} STRUCT_PACKED;
```

For a CCMP association the relevant slices are the first three 16-byte
blocks, and their roles are strictly separated. (The `tk2`/`auth`
union is TKIP's, where the 128-bit temporal key is followed by two
64-bit Michael MIC keys, one per direction; `driver.h` in the same
release documents the TKIP key as "16-byte temporal key, 8-byte Tx Mic
key, 8-byte Rx Mic Key", which is why 2.3's group-key path swaps the
two MIC halves before handing the key down. Current upstream names the
same three roles through `ptk.kck_len`, `ptk.kek_len`, `ptk.tk_len`,
bounded by `WPA_KCK_MAX_LEN` = 24, `WPA_KEK_MAX_LEN` = 32 and
`WPA_TK_MAX_LEN` = 32 (`src/common/wpa_common.h` of the pinned
`hostapd-2.6`), because the AKMs added since 2004 need KCKs longer than
CCMP's 16 bytes.)

* **KCK** authenticates the handshake. `wpa_eapol_key_mic(kck, ver,
  msg, msg_len, key_mic)` (`report/snippets/upstream/wpa_23.c`, which
  dispatches to HMAC-SHA1 for the RSN descriptor version) is what the
  client verifies on Msg3 and what it computes for Msg4.
* **KEK** protects the Key Data field, the only confidential part of
  Msg3 and of the group key handshake. In 2.3 that is AES-WRAP,
  `aes_unwrap(sm->ptk.kek, 16, *key_data_len / 8, ...)`: this is how
  the GTK reaches the client. Current upstream uses AES-SIV for the
  same field (`report/snippets/upstream/wpa_cur.c`).
* **TK** (`tk1`) is the only slice that encrypts user data, and the
  only one the supplicant hands to the driver:
  `wpa_sm_set_key(sm, alg, sm->bssid, 0, 1, key_rsc, rsclen, (u8 *) sm->ptk.tk1, keylen)`
  in `wpa_supplicant_install_ptk()`, with `keylen =
  wpa_cipher_key_len(sm->pairwise_cipher)`, and `src/drivers/driver.h`
  of the same release documents the CCMP key length as 16 octets.

The KCK and KEK stay in supplicant userspace because their job is the
handshake, and the handshake lives in userspace. That separation is
why KRACK leaks neither the pairwise key nor the passphrase: the
slices that authenticate the handshake and decrypt the GTK never enter
the radio path, and the radio is exactly where the attacker is. The
attacker who forces a reinstallation can reset a counter that belongs
to the TK, and cannot reach the KCK that would let him forge the next
handshake message. This asymmetry is why Chapter 4's boundary between
"breaks confidentiality" and "does not break the crypto" follows from
the key split rather than from any property of AES.

### AES-CCMP: why one repeated (key, PN) pair is the whole attack

CCMP is AES in CCM mode, Counter mode for confidentiality and CBC-MAC
for integrity, and `src/crypto/aes-ccm.c` of the pinned
`lab/hostapd-2.6.tar.gz` shows the ordering concretely.
`aes_ccm_auth_start()` builds `B_0` as flags || nonce || message
length and runs the authentication chain first, `X_i+1 = E(K, X_i XOR
B_i)` over the associated data and then the payload;
`aes_ccm_encr_start()` and `aes_ccm_encr()` then build counter blocks
`A_i = flags || nonce || i` and produce keystream `S_i = E(K, A_i)`,
XORed against the plaintext. The MIC is computed over the *plaintext*
and appended, so the construction is MAC-then-CTR: a genuine AEAD
whose integrity is not keystream-dependent.

The IV handed to CCM is 13 bytes assembled from the frame. The CCS
paper gives the composition: "In CCMP, the IV is the concatenation of
the sender MAC address, a 48-bit nonce, and some additional flags
derived from the transmitted frame" [@krack]. The three parts are 6 +
6 + 1 bytes with no room for a random component: the MAC is the
sender's address (A2 in the 802.11 header), the 48-bit field is the
packet number, and the flags carry the frame's priority. The IV is
therefore a deterministic function of the sender's key, that sender's
sequence position, and the frame's priority, and nothing else. Block
`i` of the keystream is `E_K(IV || i)`, a pure function of the TK and
the PN. (Terminology trap, flagged in the same paper's footnote: what
the papers call the nonce is the standard's packet number, and what
they call the IV is the standard's nonce. The papers depart from the
standard consistently with each other, and this report follows the
papers.)

That is the load-bearing fact for KRACK, stated in two halves:

1. **Confidentiality is exactly keystream-dependent on never repeating
   a (TK, PN) pair.** Two frames encrypted under the same key at the
   same PN are masked by the same keystream, so ciphertext XOR yields
   plaintext XOR, and one known plaintext yields the other. No
   strengthening of AES helps: this holds for every counter-mode
   construction, and AES itself remains unbroken.
2. **The receiver cannot detect that the sender reused one.** The same
   PN that provides freshness is the replay counter, so a frame
   arriving with an already-seen PN is dropped as a replay rather than
   decrypted twice. That protects a receiver from frames *others*
   repeat; it says nothing about a sender reusing its own keystream,
   which happens entirely inside that sender's crypto engine and never
   appears on the air as an anomaly. The only thing standing between a
   client and self-inflicted keystream reuse is the invariant that a
   given TK is installed once per key.

The standard's initialisation rule is what makes that invariant
attackable. As the CCS paper quotes it, the packet number "is
incremented by one before sending each frame, used as a replay counter
by the receiver, and initialized to 0 when installing the TK [1,
§12.5.3.4.4]" [@krack]. TKIP initialises to 1 (§12.5.2.6) and GCMP to
0 (§12.5.5.4.4) under the same clause pattern. Installing a key *is*
the act of resetting the value that must never repeat, and
installation is triggered by a message the client is required to
accept more than once. Those two requirements together are the
vulnerability, and neither half of it lives in the cipher.

The driver contract closes the chain, and it is visible in the pinned
sources: `set_key` carries `seq`, documented in `src/drivers/driver.h`
as "sequence number/packet number, seq_len octets, the next packet
number to be used for in replay protection; configured for Rx keys (in
most cases, this is only used with broadcast keys and set to zero for
unicast keys)". For a pairwise RSN key, 2.3's `install_ptk` passes an
all-zero `null_rsc` for exactly that reason. The supplicant has no way
to say "install this key but keep counting": it hands over a key whose
replay counter starts at zero and trusts the layer below to obey the
standard's rule. Chapter 3's model reproduces that same contract,
which is why the PN reset in its trace belongs to the protocol and not
to the model.

### What Msg3 retransmission means: the Install bit versus the reply

The standard requires retransmission and requires the client to keep
answering it. From the CCS paper's reading of 802.11i: "802.11i states
that the AP retransmits message 1 or 3 if it did not receive a reply
[4, §8.5.3.5]. Therefore, the client must handle retransmissions of
message 1 or 3, matching the state machine of 802.11r. Additionally,
802.11i states that the client should install the PTK after processing
and replying to message 3 [4, §8.5.3.3]." [@krack] The formal state
machine is not in 802.11i at all: the amendment "does not contain a
formal state machine describing how the supplicant must implement the
4-way handshake. Instead, it only provides pseudo-code that describes
how, but not when, certain handshake messages should be processed [4,
§8.5.6]", and the detailed supplicant machine comes from 802.11r. The
supplicant machine the CCS paper reproduces from it has the states
PTK-INIT, PTK-START, PTK-NEGOTIATING and PTK-DONE, with
`Msg1 Received` moving PTK-INIT to PTK-START, where the supplicant
calculates the SNonce, computes `TPTK = CalcPTK(PMK, ANonce, SNonce)`
and sends Msg2; PTK-NEGOTIATING sets `PTK = TPTK` and sends Msg4; and
installation happens in PTK-DONE via `MLME-SETKEYS.request(PTK)` and
`MLME-SETKEYS.request(GTK)`, with `802.1X::portValid = TRUE` there too.
The figure's Msg3 edges are guarded by `!ReplayedMsg`, and the
PTK-NEGOTIATING row carries an `unconditional Msg3 Received` edge as
well, because "the state machine explicitly takes into account
retransmissions of either message 1 or 3, which occur if the
authenticator did not receive message 2 or 4, respectively. These
retransmissions use an incremented EAPOL replay counter" [@krack]. Note
what the machine does *not* have: no variable records that a key has
already been installed, which is exactly the boolean Chapter 3's fixed
model adds. Our Chapter 3 state-machine figure is that machine.

The conflict is in the message header, not in the cipher. The entry
condition for accepting Msg3 is the bare test `Msg3 Received &&
MIC-Verified && !ReplayedMsg`, a check on the EAPOL replay counter and
on the KCK-MIC, and no state about installation at all [@krack]. Msg3
carries two instructions that are individually correct and jointly
unsafe. `WPA_KEY_INFO_INSTALL` is bit 6 of the Key Info field, `/* pairwise
*/` in `src/common/wpa_common.h` of the pinned 2.3 release (the same
bit is `WPA_KEY_INFO_TXRX` when the Key Type bit says group), and what
2.3's own frame dump prints for it is "Install": `key_info &
WPA_KEY_INFO_INSTALL ? " Install" : ""` inside
`wpa_eapol_key_dump()`, which every received EAPOL-Key passes through
before the flat test below. The frame's delivery also means:
answer this frame, my reply did not arrive. 2.3's handler is a flat
`if (key_info & WPA_KEY_INFO_INSTALL) { if
(wpa_supplicant_install_ptk(sm, key)) goto failed; }` with no state
consulted, and the CCS paper's attack is precisely that the client
"still accepts retransmissions of message 3, even when it is in the
PTK-DONE state" [@krack]. Nothing in 802.11i expresses *how many
times* a derived key may be installed: the pseudo-code gives the
conditions for installation, not the frequency, and the specification
conflates "install the key" with "respond to this frame".

That the missing concept is in the specification and not only in the
code is visible in the fix. Current upstream has to invent state the
standard never asked for: `if (sm->ptk.installed) { ... "WPA: Do not
re-install same PTK to the driver"; return 0; }` at the top of
`wpa_supplicant_install_ptk()` (`report/snippets/upstream/wpa_cur.c`),
one boolean. Note what the guard does *not* change: the client still
replies with Msg4 to every retransmission, because it must. The patch
separates the two instructions the standard fused, and does it one
layer below where the ambiguity was introduced.

The deeper point is a design split with no shared vocabulary between
its halves. The handshake half (supplicant, userspace, KCK/KEK) treats
"Install" as a per-frame instruction, obeyed every time it is seen.
The data-protection half (driver or firmware, TK) treats key
installation as the start of a key's life: counters reset, slot
armed. Neither is wrong locally. The invariant CCMP needs, one
installation per key, is owned by neither party: the supplicant never
re-keys the driver, and the driver never sees a handshake. The formal
analyses agree, from the other side: the 4-way handshake, the group
key handshake and CCMP were all proven secure, and the proofs "do not
model key installation. Put differently, they do not state when the key
is installed for use by the data-confidentiality protocol" [@krack].
Chapter 7 reads this as the root cause rather than one cause among
several.

### The group key handshake, and why the RSC is a replay defence

Msg3 is not the only place keys get installed. The AP also refreshes
the GTK and distributes it with a 2-way group key handshake: Group
1/2 carries the new GTK in the KEK-encrypted Key Data plus the RSC,
the Receive Sequence Counter, which holds "the current receive replay
counter of the group key" and travels in the EAPOL-Key RSC field
[@krack] [@krack2018]. 2.3 parses the KDE's first byte as
`KeyID[bits 0-1], Tx [bit 2]` and installs the remainder with that
counter (`wpa_supplicant_pairwise_gtk()` and
`wpa_supplicant_install_gtk()`, both in
`report/snippets/upstream/wpa_23.c`). For a group key the RSC does
double duty: it seeds the receiver's replay window for broadcast and
multicast frames, and the KeyID selects which of the two group-key
slots protects a frame, which is how an AP can migrate clients onto a
new key while still sending old-key traffic [@krack2018].

This is where CVE-2017-13080 lives, and the mechanism differs from the
pairwise case in a way that makes it easier to exploit and harder to
notice. Reinstalling a group key does not give the victim keystream
reuse, because the victim is not the sender of group frames; the AP
is. What it does is disarm the victim's replay protection: once the
reinstall reinitialises the receiver's counter for a GTK that is
*already in use*, previously captured broadcast frames are accepted as
fresh [@krack]. The trigger is the same loss-driven retransmission as
for Msg3, since the AP retransmits Group 1 when Group 2 does not
arrive. Note where the fault sits: the CCS paper confirms that clients
reinitialise the replay counter of an already-in-use group key, while
the interesting variation is in AP behaviour, because installing the
new GTK only after every client has replied is the standard's rule and
some APs install it immediately, which changes what the attacker must
capture and forward but not whether the attack works [@krack]. The
group-key variant is the papers' result; Chapter 3 models only the
pairwise reset and says so. Current upstream guards the group path
with the same shape of comparison, byte-for-byte against the installed
key: `"WPA: Not reinstalling already in-use GTK to the driver
(keyidx=%d tx=%d len=%d)"` (`wpa_supplicant_install_gtk()`,
`report/snippets/upstream/wpa_cur.c`). Idempotence again, again by
invented state, again absent from the standard.

### WPA3 and SAE: how Dragonfly binds a password to a point

WPA3 replaces the passphrase-derived PMK of WPA2-Personal with SAE,
the Dragonfly password-authenticated key exchange: SAE is specified in
the 802.11 standard and, in IETF form, in RFC 7664, while WPA3 is a
certification that mandates support for it rather than a new protocol
[@dragonblood] [@rfc7664]. Its advertised advantages are exactly the
two things the 4-way handshake cannot offer: forward secrecy, and
resistance to offline dictionary attack even against a weak password,
because the password is never used as a directly testable key. The
mechanism Chapter 3 needs is how a password becomes a curve point,
because that is where SAE's own failures are.

Each peer first hunts for the Password Element (PWE), a point derived
from the password and nothing else. The pre-Dragonblood loop is
`sae_derive_pwe_ecc` in `report/snippets/upstream/sae_2.3.c`,
extracted verbatim as `report/snippets/sae_derive_pwe_pre_dragonblood.inc`:
`pwd-seed = HMAC-SHA256(MAX(MAC_A, MAC_B) || MIN(MAC_A, MAC_B),
password || counter)` (`hmac_sha256_vector(addrs, sizeof(addrs), 2,
addr, len, pwd_seed)` with `addr[0] = password`, `addr[1] =
&counter`), then `pwd-value = KDF-z(pwd-seed, "SAE Hunting and
Pecking", p)` (`sha256_prf_bits`, same file), then `pwd-value` is used
as an x-coordinate and `crypto_ec_point_solve_y_coord()` tests whether
`x^3 + ax + b` is a quadratic residue modulo `p`. If it is, that is
the PWE, with the y-sign disambiguated by the low bit of the seed
(`y_bit = pwd_seed[SHA256_MAC_LEN - 1] & 0x01`); if not, the counter
increments and the hunt continues. RFC 7664 describes the identical
procedure: the seed "is used as an x-coordinate with the equation of
the curve to check whether x^3 + a*x + b is a quadratic residue modulo
p. If it is not, then the counter is incremented, a new base and new
seed are generated, and the hunting and pecking continues"
[@rfc7664]. Both peers run the hunt independently and land on the same
point, because it is a function of the password and the two MAC
addresses only.

The hunt is the side channel. The number of counters required is a
password-dependent quantity, and the loop's exit test is a residue
decision. Pre-Dragonblood upstream masks this two ways, and neither is
enough: it runs at least `k = 4` iterations, "to protect against
side-channel attacks that attempt to determine the number of
iterations required in the loop", and keeps testing (discarding the
result) after a point is found (`sae_2.3.c`). Chapter 3 measures how
much leaks through that pad. RFC 7664 separately recommends that the
residue test blind its own input, multiplying the candidate by a
random quadratic residue or non-residue so that the test leaks nothing
about the value under test [@rfc7664]. Current upstream implements
exactly that, with `dragonfly_get_random_qr_qnr()` and
`dragonfly_is_quadratic_residue_blind()`, and replaces every
password-dependent branch with `const_time_select_*` and
`const_time_memcmp` so neither the iteration count nor the residue
result is externally observable (`sae_test_pwd_seed_ecc`,
`report/snippets/upstream/sae_cur.c`: "go through them regardless to
minimize externally observable differences in behavior").

Having the PWE, each peer masks it before sending anything. It picks
`sae_rand` (the standard's `rand`) and a mask, and sends
`commit-scalar = (rand + mask) modulo r` together with
`COMMIT-ELEMENT = inverse(scalar-op(mask, PWE))`, the verbatim comments
in `sae_derive_commit()` and `sae_derive_commit_element_ecc()` of
`sae_2.3.c`. The mask is the password's protection: an eavesdropper
who knows neither the mask nor `rand` cannot test a candidate password
against the commit. Both peers then compute the shared secret `K =
scalar-op(rand, elem-op(scalar-op(peer-commit-scalar, PWE),
PEER-COMMIT-ELEMENT))`, rejecting the point at infinity, and derive
`KCK || PMK = KDF(keyseed, "SAE KCK and PMK", (commit-scalar +
peer-commit-scalar) mod r)` (`sae_derive_keys()`, `SAE_KCK_LEN` = 32 in
`src/common/sae.h` of the pinned 2.3 release). The Confirm frames carry
tags over that material, and they are what makes the exchange an
authenticated one. They are also the target of the reflection attack: a
peer that echoes your Commit values and substitutes your own public
material for its own evaluates the same expressions and gets the same
tag [@dragonblood]. What 2.3 lacks is not arithmetic but the check that
the incoming commit differs from the one you sent, added later as the
comment carried in the current file: "Check whether
peer-commit-scalar and PEER-COMMIT-ELEMENT are same as the values we
sent which would be evidence of a reflection attack." The PMK SAE
yields then feeds the very same 4-way handshake described above. WPA3
changed how the PMK is established, not how it is used, which is why
the key-installation question did not go away with it and why Chapter 6
treats idempotent installation as a mitigation that survives the
migration.
