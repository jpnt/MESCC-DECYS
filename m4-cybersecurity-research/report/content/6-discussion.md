## Reading our results together

The two case studies come from different subsystems and different bug classes, but they fail the same way: a component is handed a value it was designed to believe. `acl.len` from a controller module; `desc.parent` from a search function whose contract silently excludes the root. On a Linux-class system each belief is backed by a wall (a fuzzer watching the path, an address space containing the corruption). On NuttX the beliefs are the design, and Section 3 explained the economics that produced them. The CVE table's shape is the same story at list scale: the bugs that got published are precisely the ones where a caller stopped checking — TCP urgent data, a size argument to malloc, a length off UART, a rename over a network socket.

What makes the pattern worth reporting to a critical-systems audience is the deployment drift. The doctrine "kernel size matters more than kernel hardening, and validation is the application's job" was formulated for a firmware running one vendor's one application on a chip with 32 KB of RAM. openvela ships NuttX as a platform for third-party applications and an app ecosystem, with a TCP/IP stack, a Bluetooth stack and a filesystem in the trusted computing base, on the argument that POSIX conformance makes Linux code portable to it. Every one of those components is the application now, and POSIX conformance — the selling point — is also the attack-surface amplifier: the APIs that make porting easy are the ones Section 2 showed carrying the bugs (sockets, file operations, the allocator).

## The reproduction experience, reported honestly

Four observations from spending a night with the sources:

1. **These bugs were not hard to find.** The vulnerable `if`-arm in `bt_uart.c` reads like a placeholder; the `DEBUGASSERT` in `fs_inoderemove.c` reads like a known gap with a comment on it. Two days of reading boundary functions turns up both, and the 2025 credit list shows how thin the pipeline is: one outside finder (Richard Jiayang Liu) reported both filesystem CVEs, and CVE-2025-35003 came from a Southeast University pair who also authored its fix [@nuttx-security]. The project policy then requires the fix to be committed "without making any reference that the commit relates to a security vulnerability" [@nuttx-security] — correct for an embargo, and a reminder that the git history will not tell you what was security-relevant. What is missing is not cleverness but repetition — no fuzzing job, no triage team, no security issue template pointed at the tree.
2. **The fix quality is good; fix *coverage* is what you must check.** PR #16179 fixed both the driver and the stack entry point in one change and shipped within a month of disclosure. But it is reasonable to ask whether the same pattern (declared length from transport, unchecked against buffer) appears elsewhere in the ~15 drivers that sit under `drivers/wireless` and `drivers/usb` — the CVE text says "HCI and UART components", singularly confident. Zephyr's equivalent process would answer that with a team and a corpus; NuttX answers it with whatever the next reader notices.
3. **Host harnesses are underrated as a research technique.** The extracted-function approach (verbatim code, stubbed glue, ASan) took hours and produced machine-checkable evidence for both CVEs; it also produced a clean negative result on the third (fs_rename), which took a day to explain. We recommend it as the default when the on-target path (QEMU with the right peripheral model) does not exist: it keeps the code under test honest while shrinking everything else.
4. **Disclosure latency is the real metric to watch.** The affected range on CVE-2025-35003 starts at 7.25. Whatever the actual first-broken commit, the project's own documentation only learned about this bug in 2025, and the fix only reached a release when the CVE did. For a fleet product, the cost of that gap is not the bug; it is every firmware image built between 7.25 and 12.9.0 that has since shipped and will never be rescanned.

## What we would advise, by role

**To an acquirer choosing an RTOS for a connected product:** treat the absence of CVEs as the absence of measurement. Ask a NuttX vendor (including Xiaomi-class platform vendors) three concrete questions: which build protections (`CONFIG_BUILD_PROTECTED`, stack canaries, MPU regions) are on, who fuzzes their firmware image, and how firmware updates reach the device. If the answers are "off", "nobody", "SD card", then the CVE list of Table 1 should be re-read as a lower bound, not a comfort.

**To a team that nonetheless must use NuttX** (footprint, licensing, or Linux-code reuse can force it): compile in the validated checks yourself at your boundary interfaces; put a length/permission check in front of every frame your product's radios, USB and debug headers can deliver; run libFuzzer harnesses against your own `net`/`wireless`/`fs` call sites in CI — the two functions in our primary case study were a two-hour harness job; and read `Documentation/security.rst` history rather than git commit messages for news — by policy the commits will not tell you.

**To the project, as an outsider with a night's data:** one fuzzing target (`nsh` over a pty plus the network stack on the QEMU `netnsh64` configuration, driven like the in-tree `nuttx_sim` tests — everything needed is already there and already builds in CI) would have caught both case studies in the first pass; it is the highest-leverage missing artifact in the ecosystem we examined.

## What the project shows about itself

NuttX has the Apache governance, the CVE discipline, a good security page, fast fixes and a real deployment base. It does not have the continuous assurance layer that its consumer-scale deployments now require. That gap, not any individual overflow, is the finding of this report.
