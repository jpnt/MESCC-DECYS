Apache NuttX is a small real-time operating system that behaves like a tiny Linux: POSIX interfaces, flat memory, one address space shared by kernel and applications. It runs inside mass-market hardware today; Xiaomi's openvela platform for wearables and smart-home devices is built directly on a NuttX fork. Yet NuttX discloses vulnerabilities slowly and its published security guidance puts input validation on the firmware developer rather than the kernel.

This report studies NuttX as a security subject. We first survey its disclosed CVE record, then analyse the kernel design choices that explain why its bug profile differs from a microkernel RTOS. We replicate two vulnerabilities as case studies: CVE-2025-35003, a missing length check in the Bluetooth HCI UART driver that lets a malformed H4 frame overflow the driver's receive buffer, and CVE-2025-48768, a missing parent check in the inode removal path that turns removal of the filesystem root into a write through a NULL pointer. Both reproductions run the verbatim upstream functions under AddressSanitizer inside a host harness, with the patched upstream code as a control; the harness, the extracted code and the sanitizer traces are in the appendix.

Against these two bugs we compare how Zephyr, the other mainstream open-source RTOS, organises the same concerns: a dedicated security team with embargoed advisories, in-tree fuzzing tooling, and a documented triage workflow. Zephyr was independently assessed by NCC Group in 2020 to contain remotely exploitable memory corruption, so the comparison is about engineering practice rather than purity. We finish with a design-philosophy chapter: what NuttX's Linux lineage costs it in security terms, where the "validation is the application's job" doctrine is defensible on an 8-bit part, and where the two case studies show it stops being one.
